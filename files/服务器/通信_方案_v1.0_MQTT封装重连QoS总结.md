# 通信_方案_v1.0_MQTT封装重连QoS总结

> **目的**：汇总 PrintWatch 云 MQTT 链路的封装设计、三层重连防线、订阅重试状态机与 QoS 策略，沉淀已踩过的坑，避免后续修改重复踩坑。
> **代码现状日期**：2026-09-20（Phase 2 数据滞后自愈闭环已落地）
> **命名依据**：《文档库管理三步铁则》模板 1（正式方案文档）
> **修改红线**：本文档描述的所有行为受 `00-最高原则`（§原则1/§原则3 MQTT 稳定性红线）与 `06-关键功能保护规范` §2 保护，改代码前必读。

## 1. 链路总览

```
Paho 回调线程（messageArrived）          IO 消费协程（Dispatchers.IO）
┌────────────────────────────┐   ReportPipe    ┌──────────────────────────┐
│ BambuMqttClient            │  ──tryOffer──▶  │ MonitorEngine.consume    │
│  只做：null检查/轻量DTO投递 │   (O(1)非阻塞)  │  ReportParser → 状态合并  │
└────────────────────────────┘                 │  → StateCenter → UI      │
        ▲ 订阅 device/{sn}/report              └──────────────────────────┘
        │ 下行 start / pushall（pw-pushall-delay 分批）
┌───────┴──────────────────────┐
│ Bambu 云 broker:8883 (TLS)   │
└──────────────────────────────┘
```

**核心铁律**：回调线程只搬运、不解析；一切耗时（Gson 解析 / DB / 文件）都在 IO 协程侧。历史上回调内联解析 + 磁盘 IO 造成消息堆积，是本项目最早的稳定性事故。

## 2. 连接封装层（`BambuMqttClient.kt`）

| 设计点 | 现状 | 为什么（含踩坑） |
|--------|------|------------------|
| 客户端 | Paho `MqttAsyncClient` + `MemoryPersistence` + `MqttCallbackExtended` | 异步 API，回调线程不被 connect/publish 阻塞 |
| ClientId | `"printwatch_" + UUID 随机`（每次连接不同） | **踩坑**：固定 ClientId 会与 Bambu Studio 等多客户端互踢掉线；随机 ID 保证共存 |
| 鉴权 | username = `u_{uid}`，password = accessToken（仅令牌刷新，不做账号登录） | 云端协议约束 |
| 传输 | `cn.mqtt.bambulab.com:8883`，TLS 开启（`Config.MQTT_TLS`），TLSv1.2 + 系统默认信任库 | 兼容拓竹云证书链，无需内置证书 |
| 业务边界 | 只读订阅 `device/{sn}/report`；下行仅 `start` / `pushall` 两条指令 | APP 是纯监控端，不控制打印机 |
| 断开 | `disconnectForcibly(2000, 2000)` + `close()`，先 `cancelAll()` 状态机、`shutdownNow()` 调度器 | 防重连任务泄漏；回调置空防停机期间残余回调 |

### 下行指令时序（connectComplete 内）

1. `start`：**立即**发（延迟 0ms）——启用持续推送；
2. `pushall`：**延迟 2 秒**发——**踩坑**：部分机型立即发 pushall 返回的快照不含 `gcode_state`/温度，必须等 `start` 生效后再拉全量。

两者 payload 统一为 `{"pushing":{"sequence_id":"0","command":"..."}}`。

### 下行分批（唯一实现 `notifyDevicesBySns`，禁止复制第二份）

- 批大小 `MQTT_NOTIFY_BATCH_SIZE=10` 台，批间 `MQTT_NOTIFY_BATCH_INTERVAL_MS=300ms`；
- **踩坑**：20 台=40 条、40 台=80 条瞬时 PUBLISH 会阻塞回调线程并触发 broker 限流甚至重连循环 → 必须在 `pw-pushall-delay` 后台单线程分批发；批内 `sleep` 只允许发生在该专用线程（回调线程/主线程禁止）；
- `requestPushAll(sns)`（Phase 2）：按 SN 补拉入口，schedule-only 不阻塞调用方，与 connectComplete 路径共用同一分批核。

## 3. 重连策略（三层防线，禁止自建第四层）

| 层 | 触发 | 动作 | 关键参数 |
|----|------|------|----------|
| L1 | 传输层断开 | **Paho 自动重连**（`isAutomaticReconnect=true`），`connectionLost` 只上报状态、不自建重连循环 | `maxReconnectDelay=30s`（`MAX_RECONNECT_BACKOFF_MS`）、`keepAlive=30s`、`connectionTimeout=15s`、`cleanSession=true` |
| L2 | 连接失败且 `authRejected`（MqttException reasonCode **4/5**） | 刷新 accessToken 一次后用新 token 重连 | 区分「token 过期」与普通网络失败，避免无效重试 |
| L3 | 会话级异常（订阅耗尽 / `SESSION_SILENT_MS=120s` 零报文） | MonitorEngine `rateLimitMqttRestart` 重建会话 | 全局限速 `RESTART_MIN_INTERVAL_MS=5min`，**延迟挂起合并**语义（间隔内多次触发合并为一次，不是丢弃） |

**L3 三重守护**（`handleSubscribeExhausted`，缺一不可，防止重建僵尸连接）：
1. 监控已停止（`started=false`）→ 丢弃；
2. epoch 不等于当前会话（已被外部事件重建）→ 丢弃；
3. broker 未连接 → 丢弃，交给 L1 Paho 自动重连，**不互搏**。

**会话代际 `mqttEpoch`**：每次重建连接递增；所有异步回调（订阅重试/耗尽/限速重启）执行前校验 epoch，旧代际任务自动失效。**任何新增异步路径都必须带 epoch 校验**，否则停机/重建后会跑出僵尸任务。

> ⚠️ **禁止**：移除/绕过 L1 自动重连；在 `connectionLost` 里 sleep/重试；修改 keepAlive/超时无评估；L3 直接 `disconnect()`（会 `shutdownNow` 调度器造成回调自中断，必须走 `rateLimitMqttRestart`）。

## 4. 订阅可靠性（`SubscribeRetryStateMachine.kt`，Phase 2）

**背景踩坑**：Paho `subscribe()` 是 fire-and-forget，订阅失败/ACK 丢失完全静默 → 表现为「连接正常但数据滞流」，极难排查。

**机制**：
- 每 topic 挂 `IMqttActionListener` + **ACK 超时观察**（Paho 无内建订阅超时）；
- 退避 `SUBSCRIBE_RETRY_BACKOFF_MS = [1s, 3s, 6s]`，`maxAttempts = 3+1 = 4` 次；
- ACK 超时 `SUBSCRIBE_ACK_TIMEOUT_MS = 15s`，**必须 > 最长退避档（6s）+ RTT 余量**，否则会被下一轮调度过早打断（取值约束写在 Config 注释里，改退避必须联动检查）；
- 超时与失败合并为同一重试计数入口；全部耗尽后**一次性**聚合回调 `onSubscribeExhausted(failedSns, totalRetries)`（`exhaustedFired` CAS 防重复）。

**线程契约（单测覆盖的不变量，勿破坏）**：
- 共用 `pw-pushall-delay` 单线程调度器 → 所有集合状态变更天然串行，**零 synchronized**（合规 01 §7 同步锁禁令）；
- `epoch` / `exhaustedFired` / `totalRetries` 是仅有的跨线程字段，均为 Atomic；
- Paho 网络线程的 onSuccess/onFailure 一律 marshal 回调度器再碰共享状态；
- `onExhausted` 回调运行在 `pw-pushall-delay` 线程：**禁止**在回调体内同步等待 / `Thread.sleep` / `disconnect()`；上层（MonitorEngine）必须立即跳 IO 协程；
- 重复进入（重连触发 `subscribeTopics`）靠 epoch 递增使旧轮全部失效，单线程 FIFO 保证清理在新轮之前执行。

**灰度开关**：`Config.GRAYSCALE_DATA_FIX=false` 时状态机不创建，退回 fire-and-forget 订阅，行为等价 Phase 1（回滚通道，勿删）。

## 5. QoS 策略（当前全部 QoS 0，有意为之）

| 方向 | QoS | 理由 |
|------|-----|------|
| 订阅 report（`device/{sn}/report`） | 0 | 高频状态上报，单条丢失可容忍——下一条报文天然覆盖；监控场景无一条不可丢的数据 |
| 发布 start/pushall | 0 | 可靠性不靠 QoS 补偿，靠**重连后 `connectComplete` 重发两条指令**兜底（含 Paho 自动重连成功的场景） |
| ManualAcks | `false` | 配合 QoS0，无手动确认需求 |

**可靠性等价物（改 QoS 前先看这里）**：
1. 短暂断线丢报 → 重连成功后 `pushall` 拉全量快照补偿；
2. 高频洪峰背压 → ReportPipe **丢旧保新**（见 §6），而不是 QoS1 重复投递堆积；
3. 订阅丢失 → 订阅重试状态机 + L3 会话重建。

> ⚠️ **不要**因为「担心丢消息」改 QoS1/2：cleanSession=true 下重连后 QoS1 未确认消息本来也不续传，只会增加 broker 与回调线程负担；真缺数据走 pushall 补拉才是既定路线。

## 6. 背压管道（`ReportPipe.kt`，回调线程 → IO 的唯一出口）

| 特性 | 值 | 说明 |
|------|-----|------|
| 容量 | `REPORT_PIPE_CAPACITY=256` | 背压缓冲上限，禁止无限堆积拖垮回调线程 |
| 投递 | `tryOffer` O(1) 非阻塞 | **禁止**改回挂起式 `send`（会阻塞回调线程，违反 00 §原则3） |
| 溢出策略 | **丢旧保新**：缓冲满弹队头最旧、再投新报 | **踩坑**：原策略丢最新导致监控数据滞后；监控数据价值随时间单调递减，丢旧才是正确方向 |
| 丢弃可观测 | 总量 StateFlow + 按设备 ConcurrentHashMap + 限频日志（`PIPE_DROP_LOG_MIN_INTERVAL_MS=10s`） | 19 台洪峰时不刷屏 logcat |
| 生命周期 | `drainNow()` 主动清栈（不计丢弃数）；`close()` 后不可复用 | 停机/重建前清陈旧数据 |

## 8. 踩坑红线速查（改代码前过一遍）

| # | 踩坑 | 正确做法 |
|---|------|----------|
| 1 | 回调线程内解析/磁盘 IO → 消息堆积、状态延迟 | 回调只 `tryOffer` 轻量 DTO，解析在 IO 协程（00 §原则3） |
| 2 | 固定 ClientId → 与其他客户端互踢 | 每次连接随机 UUID |
| 3 | 回调线程批量 publish → broker 限流/重连循环 | pw-pushall-delay 分批（10 台/300ms） |
| 4 | pushall 立即发 → 部分机型快照缺 gcode_state/温度 | start 立即、pushall 延迟 2s |
| 5 | 管道溢出丢最新 → 数据滞后 | 丢旧保新 + 丢弃计数可观测 |
| 6 | 订阅 fire-and-forget 静默失败 → 数据滞流 | 订阅重试状态机（listener + ACK 超时 + 退避） |
| 7 | ACK 超时 < 退避档 → 重试被过早打断 | 15s > 最长退避 6s，联动修改 |
| 8 | `onExhausted` 回调内 `disconnect()` → shutdownNow 自中断 | 回调只跳线程，重建走 `rateLimitMqttRestart` |
| 9 | 无 epoch 校验的异步任务 → 停机后僵尸连接/僵尸任务 | 所有异步路径执行前校验会话代际 |
| 10 | 自建重连循环与 Paho 自动重连互搏 | connectionLost 只上报；L3 有三重守护 + 5min 限速 |
