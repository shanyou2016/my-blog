## 1. 背景与架构分层

### 1.1 为什么是 MAVLink（历史决策）

最早 APP 使用**私有二进制协议** `0xEB 0x90`（8 字节固定帧 + XOR 校验，见 `协议_手册_通用协议指南.md` 第一章），
以及手写的 `MavLinkEncoder / MavLinkDecoder / MavLinkMessage / MsgXxx` 系列（手算字节偏移 + 手写 CRC）。

**手写协议的三宗罪**（2026-05 集成复盘，见 `协议_集成_MAVLink完整接入.md`）：

1. CRC 校验不完整、覆盖范围靠人记（集成首个致命错误就是"STX 被误算进 CRC"）；
2. 字段类型/字节序易错，且**类型声明与 pack 不一致**（生成器特性，见 §4.2）；
3. 扩展新消息要动大量手工代码，双端（App / 固件）各写一版实现，天然双真源。

**迁移方案**：引入 MAVLink 官方 mavgen 工具，从固件的 XML 定义生成 Java 代码（生成产物落在
`core/.../protocol/mavlink/lib/` 下），APP 侧只保留一个协议门面 `MavLinkManager`。
私有 `0xEB90` 协议仅剩 8 字节控制帧残留（`ProtocolCodec.parseRobotStatus` 已 `@Deprecated` 返回 null）。

### 1.2 三种承载模式（MAVLink 字节流的三种运输方式）

`MavLinkManager` 本身**零网络 I/O**：字节由上层注入（`feed`），发送经注入的 `SendDelegate` 外发。
三种通信模式下由不同的 :app 组件承载：

| 模式 | 承载组件 | 接收注入点 | 发送委托 |
|------|---------|-----------|---------|
| TCP 客户端（单机直连） | `TCPCommunicationManager` | `recvLoop`（线程 `tcp-recv`，MAX_PRIORITY） | `sendExec` 单线程池（队列上限 32，超限丢新帧） |
| TCP 服务端（一对多） | `TCPServerManager` + `RobotClientSession` | `RobotClientSession.onData` | `sendToSelected()`（按 robotId 路由 + 动态 `setTargetSysId`） |
| UDP / 水星网桥 | `WiFiCommunicationManager` | 接收回调 | 同构发送门面 |

> 三者的 MAVLink 解析/编码路径完全同构，差异只在"字节从哪来、发到哪去"。
> 心跳 1Hz 统一由 `HeartbeatModule` 驱动（`sendStandardHeartbeat()` → `MavLinkManager.sendHeartbeat()`）。

### 1.3 分层（谁负责什么）

```
机器人固件 ──TCP/UDP 字节流──▶ :app 通信层（Socket / 线程 / 注入）
                                    │  feed(byte[], len)
                                    ▼
                     :core 纯协议层 MavLinkManager（零 Android 依赖）
                     ├─ Parser 逐字节状态机（v1/v2、CRC、丢包统计）
                     ├─ 按 msgid 分发到 5 类 Listener（DispatchExecutor 派发线程）
                     └─ sendXxx()：pack → encodePacket → SendDelegate
                                    │
                                    ▼
          :app 状态层 MavLinkStateAdapter（唯一字段映射点）
                                    │  StateCenter.robotStatusChannel / robotAttitudeChannel
                                    ▼
   消费端：UI（RobotStatusPresenter）/ 黑匣子（BlackboxModule）/ 设备列表（RobotDeviceManager）
```

**关键架构约束**（HARNESS 注解在案）：
- `:core` 纯 Java，**禁止引入 `android.util.Log`**，协议编码失败的 `catch` 静默丢弃是**设计契约**；
- `MavLinkManager` 自身不加锁、不建线程，线程安全由调用方保证（保护 MAX_PRIORITY 接收线程不被阻塞）；
- 字段映射**只允许**在 `MavLinkStateAdapter` 一处发生（其余消费端只读 StateCenter）。

## 2. 解析机制（收方向）

### 2.1 收包入口：`feed()` 逐字节注入

```java
// MavLinkManager.feed(byte[] data, int length)
for (int i = 0; i < length; i++) {
    MAVLinkPacket p = mavParser.mavlink_parse_char(data[i] & 0xFF);
    if (p != null) handleReceivedPacket(p);
}
```

- `Parser` 是**有状态增量状态机**：跨 `feed()` 调用保持解析进度，天然正确处理 **TCP 粘包 / 半包 / 一次 read 多帧**；
- 解析动作发生在**接收线程**（`tcp-recv` 等），单帧解析为 O(1) 内存操作，满足 TCP < 500ms 红线；
- **断连/重连必须 `reset()` 重建 Parser**（`TCPCommunicationManager.onStart`、`triggerReconnect`），
  否则上一连接的半截残字节会污染新连接的流。

### 2.2 帧结构与 v1/v2 自动切换

| 版本 | 帧结构 | 说明 |
|------|--------|------|
| v1（STX=0xFE） | `FE | len | seq | sysid | compid | msgid | payload | crc_lo crc_hi` | 6 字节头 |
| v2（STX=0xFD） | `FD | len | incompat | compat | seq | sysid | compid | msgid×3 | payload | crc_lo crc_hi` | 10 字节头，可含签名 |

- **STX 字节决定版本**，同一字节流内 v1/v2 可混用（现状：机器人状态帧走 v2，App 发送心跳为 v1 帧）；
- v2 `incompatFlags ∉ {0,1}` → 丢帧；`incompatFlags==0x01`（签名帧）**本项目未实现，按 crcError 丢弃**；
- payload 缓冲区容量 255 字节（`MAVLinkPayload` 的 `ByteBuffer`），超长由协议层拒绝。

### 2.3 CRC 校验（本项目实测约定）

- 算法：**CRC-16/MCRF4XX**，初值 `0xFFFF`；
- 覆盖范围（`MAVLinkPacket.generateCRC`，**STX 不参与**）：
  - v2：`len, incompat, compat, seq, sysid, compid, msgid×3`（9 字节头）+ payload + **crc_extra**；
  - v1：`len, seq, sysid, compid, msgid`（5 字节头）+ payload + **crc_extra**；
- 最后一步 `crc.finish_checksum(msgid)` 追加 **crc_extra（magic byte）**；
- ⚠️ **crc_extra 表中缺某 msgid 时**：`finish_checksum` 返回 `false`，**帧仍会被发出**（`encodePacket` 不检查返回值）
  → 生成"少一个 magic byte"的 CRC 帧；收侧则直接判 crcError **整包丢弃**。
  该机制是 §4.3「205/206/207 被删致日志下载双向静默失效」的根因，也是 §7.1 心跳风险的来源；
- 实网验证：现场 944 帧逐帧校验 **100% 通过**（2026-09-13 线侧抓包，见 §4.8）。

### 2.4 长度守卫（必需，不是可选项）

```java
// MavLinkManager.handleReceivedPacket，case 200：
private static final int LEGACY_WINDOW_ROBOT_STATUS_LEN = 66;   // = 上一版长度
if (statusPayloadLen <= LEGACY_WINDOW_ROBOT_STATUS_LEN) {
    legacyStatusFrameCount++;   // 拒绝分发 + 计数
    break;
}
```

**为什么必须有**：`MAVLinkPayload` 底层 `ByteBuffer` 容量 255，`unpack()` **越界读不抛异常，而是读 0**。
若固件仍发 66 字节旧布局，`climb_height / screw_pos / pressure_state / swbits` 等新字段会整体错位，
解析"成功"但数值全错，**静默污染** UI、黑匣子与告警判据。

**判据为什么取「≤ 上一版长度」而不是「< 新版长度」**：MAVLink v2 允许**截断尾部零字节**（`mavTrimPayload`），
实际长度可落在 67~81 之间，属合法帧，不得误杀（仅由 :app 侧一次性诊断日志提示）。

> 每版协议升级时，这个常量必须同步改为**上一版长度**。配套诊断：
> `getLastRobotStatusPayloadLen()` / `getLegacyStatusFrameCount()` → :app 侧 tag `MavLinkFrame`。

### 2.5 `unpack()` 的越界语义（解析侧最大陷阱）

- 字段声明类型**不可信**（见 §4.2）：`int work_mode` 实际按 `putUnsignedShort` 读写；
- 截断帧（尾部零字节被裁）在接收侧**必须按声明长度补零**后再 `unpack`，
  `MavlinkParser.buildPayload` 即按 `MAVLINK_MSG_LENGTH` 定长构造（调试工具专用，见 §7.2）。

### 2.6 分发矩阵（msgid → Listener → 线程）

| msgid | 处理 | 派发线程 | 下游 |
|-------|------|---------|------|
| 200 | **长度守卫 → 构造消息** | `mainExecutor.post`（主线程） | `StatusListener` → `MavLinkStateAdapter` |
| 202 | 构造消息 | `mainExecutor.post` | `ParamListener` → `MainControlPanelController`（回执单飞校验） |
| 204 | **数组聚合**（`obs_index==0` 清缓存；`size==obs_total` 才回调） | `mainExecutor.post` | `ObstacleListener` → `MainUIActivity` |
| 206 | 构造消息 | `mainExecutor.post` | `FileListResponseListener` → `RobotControlService` → `robotFileListChannel` |
| 207 | 构造消息 | **调用线程同步**（唯一特例） | `FileDataListener` → `EventChannel.BACKGROUND` 负责调度 |
| 0 / 其它 | 静默忽略（`default`） | — | — |

> **207 为什么同步**：文件数据块 134B/帧、高频到达，若每帧都 post 主线程会造成主线程洪泛；
> 约定"下游 BACKGROUND 通道自行调度"，编解码留在接收线程完成（P1 架构决策，代码有注释在案）。
>

## 3. 使用指南（发方向 & 接入）

### 3.1 发送链路

```
业务层（手柄/参数/文件/心跳）
```

## 4. 踩坑集（12 条，均为真实验证过的教训）

> 每条按「现象 → 根因 → 处置 → 教训」组织。**教训一栏是防重复犯错的检查项**。

### 4.1 CRC 覆盖范围把 STX 算进去 → 双端全部拒收

- **现象**：平板收到帧但解析不了，弹窗显示"收到 UDP 明文消息"而不是"收到 MAVLink 消息"。
- **根因**：测试脚本 `struct.pack('<BBBBBBB', 0xFD, ...)` 把 STX 算进 CRC 输入；协议规定 **STX 不参与 CRC**。
- **处置**：STX 单独提取，CRC 从 LEN 开始算（见 §2.3）。
- **教训**：协议字段/校验范围**必须查参考实现代码**（`generateCRC`），不凭印象。

### 4.2 字段类型以"声明"为准 → 字节数全错

- **现象**：Python 组包字段错位，Java 解析出乱值。
- **根因**：MAVLink Java 生成器**字段声明类型与 `pack()/unpack()` 实际使用类型不一致**
  （如 `public int battery_volt` 实际 `putUnsignedShort` 2 字节）。依据见 `协议_问题_脚本修复.md`。
- **处置**：所有外部语言实现**一律按 `pack()/unpack()` 的写入序列 + 实际方法类型**构造数据。
- **教训**：判类型看**方法名**（`putUnsignedShort` = u16），不看字段声明。

### 4.3 crc_extra 手工维护 + "局部重新生成" 删表项 → 日志下载双向静默失效（P0，2026-09-11）

- **现象**：机器人日志下载整链失效——列表拉不到、下载无数据，但**无任何报错**。
- **根因**：固件 XML 局部重新生成只覆盖 200/202/203/204，`CRC.java` 中 **205/206/207 三条被删除**：
  - 收侧：`Parser` 末态 `generateCRC()` 缺表项 → 206/207 **整包丢弃**；
  - 发侧：`encodePacket()` 缺 crc_extra → 205 请求帧 CRC 错误 → 固件丢弃。
- **处置**：按脚本权威值补齐 **205=94 / 206=95 / 207=65**（脚本计算 = 历史值 = 模拟器常量，三方一致）；
  加防误删注释固化；pre-commit Step 3F + CI 红线双重门禁。
- **教训**：crc_extra 与消息类字段布局**强耦合且零编译期保护**，必须"机器生成 + 双向校验"，禁止人工回忆改两处。

### 4.4 `char` 与 `int8_t` 二义性 → crc_extra 误算 227（2026-09-10）

- **现象**：本地权威计算脚本对 206 号包算出 227，历史/模拟器值均为 95。
- **根因**：MAVLink Java 生成器对 XML `char[N]` 与 `int8_t[N]` 都输出 `byte[] + putByte/getByte`，看声明无法区分；
  按 `int8_t[48]` 误算得 227。
- **处置**：生成器**只为 `char[N]` 生成 `setXxx(String)` 字符串访问器**（`msg_file_list_response.filename` 即 `char[48]`），
  脚本据此判别。
- **教训**：判别依据要找"生成器行为的稳定差异"，而不是猜类型。

### 4.5 无长度守卫 → 旧固件发旧布局，"解析成功但数值全错"（2026-09-11）

- **现象**：协议升级后若固件未同步升级，UI 数值整体错位但不报错。
- **根因**：`MAVLinkPayload` 底层 `ByteBuffer` 容量 255，`unpack()` 越界读**读 0 不抛异常**。
- **处置**：200 号包入口长度守卫（§2.4）+ `MavLinkFrame` 一次性诊断日志。
- **教训**：协议升级必须配套**版本判据**；对"静默错位"的设计要用显式守卫拦截，而不是指望下游发现。

### 4.6 手工字节偏移与生成类双真源（2026-09-10 收口）

- **现象**：`ui/utils/MavlinkParser.java` 调试面板与真实链路对同一帧解析结果可能不一致。
- **根因**：调试解析器硬编码字节偏移常量，与 mavgen 生成类**各写一套布局**。
- **处置**：改为**委托生成类 `unpack()`**，删除全部硬编码偏移；布局真源收敛为一处。
- **教训**：同一协议**只允许一个布局真源**；调试工具也必须复用主链路解析代码。

### 4.7 私有心跳被标准 MAVLink 心跳替代（历史）

- **旧**：`0xEB 0x90 0x00 0x01 0x00` 私有五字节心跳，C 端 / Python 端都无法识别。
- **新**：标准 MAVLink v1 HEARTBEAT（msgid=0，9 字节 payload），全生态工具可识别。
- **遗留**：见 §7.1——标准 HEARTBEAT 的 crc_extra（50）**未登记进 CRC 表**。

### 4.8 固件故障态脏值 → 线侧独立取证（2026-09-13，App 侧无责的标准范例）

- **现象**：机器人报故障期间，丝杆值与上负压开度满屏乱跳（超出协议合法域）。
- **取证方法**（**可复用的方法论**）：平板提权后 `tcpdump` 在 App 之外独立抓包，
  用独立解码脚本按"含头部 CRC + extra"逐帧校验，对 **944 帧 CRC 合法帧**做统计。
- **结论**：偏移 55（`screw_limit` 当时为 i8）与 56（`up_vacuum_power` 当时为 u8）为白噪声
  （相邻帧差均值 84，均匀分布）；其余字段正常；**App 解析链路 100% 正确，根因在固件故障分支**。
- **副产品**：证明 App 解析链正确的最好方式 = **绕过 App 抓包独立解码**，而不是在 App 日志里猜。
- **教训**：① 数据异常先分"链路错位 vs 源头脏值"；② 越界值**禁止静默钳制**（钳制会掩盖固件缺陷）；
  ③ 见 §5.2——其后固件把相关字段从 u8/i8 **拓宽为 u16/i16**（零窄化），从根上消除截断掩盖。

### 4.9 工具链脚本版本漂移（2026-09-11 收口）

- **现象**：同步前各脚本 200 号包长度出现 **61/50/36/32/28 五种**，crc_extra 出现 **181/122/63/252/85 五种**。
- **根因**：协议每次升级只改主链路，`tools/` 下脚本各自为政、无人校验。
- **处置**：全部收敛；新增 `check_mavlink_tool_layouts.py` 静态门禁（旧布局字面量/旧 crc 值/缺失新字段即 ERROR）。
- **教训**：**工具链与主链路同源同版本**，否则联调时"App 是好的、脚本是旧的"，排查方向被带偏。

### 4.10 u8/i8 被越界值截断掩盖（2026-09-13 类型拓宽）

- **现象**：脏值在 u8 域只表现为"随机 0~255"，**无法区分"真实 255"与"负值被截断"**。
- **处置**：2026-09-13 把 `work_mode/climb_speed/err_code/screw_limit/up_vacuum_power/down_vacuum_power/fans_on`
  从 u8/i8 **拓宽为 u16/i16**（59→66 字节），配合 §3.4 第 4 步"零窄化透传"原则。
- **教训**：安全相关字段宁可多占字节，不做窄类型截断（截断 = 信息丢失 = 掩盖源头缺陷）。

### 4.11 黑匣子 CSV 版式与协议强耦合 → 魔数分流

- **现象**：协议每扩字段，黑匣子列数变化；旧文件与旧解析脚本互相读不懂。
- **处置**：魔数分流 `#BLACKBOX_V1/V2/V3/V4` + `COLUMNS_V*` 常量 + `fromCsvLine(line, magic)`；
  `CSV_HEADER` 收口为 `BlackboxEntry.CSV_COLUMNS_V4` 派生单一真源（曾修正"表头 21 列 vs 数据 29 列"错位）。
- **教训**：持久化格式**必须自带版本魔数**；解析必须按魔数严格分流，禁止"一个解析器猜所有版本"。

### 4.12 注释与常量漂移（现存，见 §7）

- **现象**：`MavLinkManager` 长度守卫常量为 `66`，但字段注释残留"≤59 字节"旧描述。
- **教训**：协议升级时**注释与常量必须同批改**；文档（本文）与代码的"上一版长度"是每版必改的三个点之一。

## 7. 已知风险与遗留（诚实清单）

### 7.1 【P1，建议尽快收口】CRC 表缺 msgid 0（标准 HEARTBEAT，官方 50）

- **事实**：`CRC.java` 仅登记 7 条自定义消息（200~207），**无 msgid 0**；
  `sendHeartbeat()` 组帧后 `finish_checksum(0)` 返回 `false`，CRC **少了 magic byte**，但帧**照常发出**（§2.3）。
- **影响**：严格按标准校验心跳的对端会判 CRC 失败。现网联调正常，说明当前固件可能不校验或采用同款实现，
  但这是**跨实现对接隐患**（第三方工具、固件升级后都可能暴露）。
- **现有盲区**：`verify_mavlink_crc_extra.py` 只遍历 `msg_*.java`（无 `msg_heartbeat` 类），**该缺口不会被门禁发现**。
- **建议动作**：① CRC 表补 `put(0, 50)`；② 脚本增加标准消息覆盖或至少增加"心跳 CRC 自检"断言；
  ③ 用 `test_multi_sysid.py`（按 50 复算）回归验证。

### 7.2 【P2】`MAVLinkPacket.unpack()` 缺 205/206/207 分支

生成产物"局部重新生成"痕迹：`unpack()` 只识别 200/202/203/204。
当前不影响运行（`MavLinkManager` 直接 `new msg_xxx(packet)` 绕开了它），但**与 CRC 表不一致**，
后续若有人改用 `unpack()` 统一分派会踩坑。建议补齐或加注释说明。

### 7.3 【P2】长度守卫注释漂移

`MavLinkManager` 行内注释残留"≤59 字节"表述，实际常量已为 `66`。协议每次升级时须同批修正
（常量 / 注释 / 本文 §5.2 三处）。

### 7.4 【P2】C 侧模拟器与部分脚本 stale

`robot_simulator.c`、`robot_client_simulator.c` 等仍按 **59 字节 / crc 111**（及 202=89）构造报文；
`check_mavlink_tool_layouts.py` 对 `.c/.h` 仅 WARN 不阻断。本地联调**优先用 `fake_robot_server.py`**。

### 7.5 【观察项】语义/契约待确认

| # | 项 | 现状策略 |
|---|-----|---------|
| 1 | `yaw_sp / yaw_err` 单位未定义（度 or 弧度，误换算差 57 倍） | **原始值透传**，UI 标注"（原始值）"，禁止擅自换算 |
| 2 | `fans_on` 只定义 0上锁/1解锁，异常取值未定义 | 显式显示 `异常值(N)` 并标红，**不静默归零**（涵道与吸附安全相关） |
| 3 | 202 号包上行回显字段（`moveing_vaccum_grade`/`work_mode`）未补齐 | `MainControlPanelController` 有 TODO，回执回读暂只用于越障单飞校验 |

| 7 | 204 障碍物聚合强依赖 `obs_total` 准确 | `obs_total` 不符时列表永不回调（无超时兜底） |

## 附录 B：故障速查表

| 症状 | 第一嫌疑 | 排查动作 |
|------|---------|---------|
| 状态数值整体错位 / 显示异常但无报错 | 固件协议版本与 App 不一致（长度不符） | `adb logcat -s MavLinkFrame` 看"实际长度 vs 期望 82"；核对长度守卫计数值 |
| 某类消息**完全不到达**（如日志列表） | CRC 表缺条目 → Parser 整包丢弃 | `python3 scripts/verify_mavlink_crc_extra.py`（看死条目/PASS） |
| 单个字段乱跳、越界 | 源头脏值 vs 解析错位二选一 | 线侧 `tcpdump` + 独立解码统计（抄 §4.8 方法），不要只在 App 内猜 |
| 心跳对端不识别 | msgid 0 缺 crc_extra（§7.1） | 看对端是否严格校验；补表 50 后回归 |
| 联调脚本发的帧 App 收不到 | 脚本版本 stale | `python3 scripts/check_mavlink_tool_layouts.py` |
| 切换机器人后解析混乱 | Parser 未 reset | 检查 `onStart/triggerReconnect` 是否调用 `reset()` |
| 数值单位疑似不对（水平角/误差） | 单位未定义（§7.5-1） | 禁止换算，按原始值比对固件日志 |
